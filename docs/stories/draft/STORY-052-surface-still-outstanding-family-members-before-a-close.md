# STORY-052: Surface still-outstanding family members before a close

**Reported**: 2026-07-26
**Problems**: P433
**JTBD**: JTBD-006 (secondary: JTBD-001)
**RFCs**: RFC-056
**Story Maps**: STORY-MAP-009
**Estimated effort**: M

## User value (required, INVEST Valuable)

In order to know that closing a ticket settles the work it belongs with, rather than quietly
leaving related tickets behind, as a developer draining a WSJF backlog — often while away from
the keyboard — I want each close path to tell me which tickets the closing one is recorded as
composing with are still outstanding, and to put that call in front of me instead of making it
silently or blocking on it.

The edges already exist. Maintainers have authored 212 `**Composes with**` references across the
open, known-error and verifying corpus, and nothing reads a single one of them. Twenty-nine
tickets have already closed naming a sibling that is still open or known-error today; in none of
those closes was the edge surfaced, so nobody decided whether it should have closed too. This
story makes the authored edge do work at the one moment it matters.

## Acceptance criteria (accepted-gate, INVEST Testable)

- [ ] Given a ticket whose `## Dependencies` section names a `**Composes with**` sibling that is
  currently under `docs/problems/open/`, the scan emits a line identifying that sibling. Given the
  same ticket where the named sibling is under `docs/problems/verifying/`, `parked/` or `closed/`,
  the scan emits nothing for it.
- [ ] Given a ticket that names no siblings, but which another still-actionable ticket names on its
  own `**Composes with**` line, the scan emits a line for that reverse edge. Forward and reverse
  edges resolving to the same sibling are reported once, not twice.
- [ ] Given a ticket with no family edges in either direction, the scan emits no lines and exits 0.
- [ ] The scan exits 0 on every input, including a malformed or missing ticket path, so no close
  path can be halted by it.
- [ ] The scan is reachable as `wr-itil-scan-sibling-family` from a shell whose `PATH` contains only
  the installed plugin's `bin/`, with no repo checkout present — proving the ADR-049 shim resolves
  for an adopter and not merely inside this monorepo.
- [ ] Closing a ticket with a still-actionable sibling through `/wr-itil:transition-problem <NNN>
  close` leaves a durable record that the sibling was surfaced and the close proceeded anyway — not
  only a line in a transcript. Under AFK that record is an `outstanding_questions` entry naming the
  closing ticket, each still-actionable sibling, and the three dispositions (closes with this
  ticket, gets re-linked, knowingly left open). This criterion is the one JTBD-006's audit-trail
  constraint turns on: an advisory nobody can read afterwards leaves the defect unfixed for exactly
  the unattended case the job governs.
- [ ] The same surfacing happens when the close is reached through `/wr-itil:review-problems` Step 4
  Bucket 1, through its Step 4.6 relevance-close pass, and through `/wr-retrospective:run-retro`
  Step 4a. The first two rename the ticket themselves rather than dispatching through
  `transition-problem`, so covering only that skill leaves them uncovered.
- [ ] A batch close of several tickets that each have stranded siblings produces ONE surfaced
  decision covering them all, not one per ticket.
- [ ] Every assertion above is exercised by bats driving the script and the skills against fixture
  ticket trees, asserting on emitted lines and written records. No test asserts on the prose content
  of a SKILL.md.

## Implementation notes

Scope, the rejected gate-strength alternatives, and the deferred Phase 2 (friction-class keyword
clustering) are in RFC-056. The shim wrapper is generated by `scripts/sync-shim-wrappers.sh` from
`packages/shared/lib/shim-wrapper-template.sh` per ADR-080 — do not hand-author the three-line
`exec` form the ADR-049 body still shows.

One design question is unresolved and is queued for ratification: whether the gate is
advisory-plus-queue as scoped here, plain advisory, or halting. RFC-056 argues advisory-plus-queue
and the architect concurs, but the maintainer has not ratified it. That ratification is the same
event that moves this story to `accepted`, so it is not a separate blocker.
