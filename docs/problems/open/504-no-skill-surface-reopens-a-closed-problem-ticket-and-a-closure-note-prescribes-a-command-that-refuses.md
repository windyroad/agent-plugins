# Problem 504: No skill surface reopens a closed problem ticket, and closure notes prescribe a command that refuses

**Status**: Open
**Reported**: 2026-08-20
**Priority**: 6 (Medium) — Impact: 2 × Likelihood: 3 — derived at capture. Impact 2: the reopen still happens, just by hand, outside the skill that owns lifecycle transitions — so the P057 re-stage, P062 README refresh and ADR-014 commit discipline all rest on the agent remembering them rather than on the skill. Likelihood 3: reopening is uncommon, but a closure that turns out to be wrong is exactly the case where the lifecycle tooling should be most reliable, and this repo has 236 closed tickets.
**Origin**: internal
**Effort**: S — derived at capture: one row in the transition-problem validation table plus the pre-flight and Status-edit branch, mirroring the three existing directions. Sized against P071's other phased transition work.
**JTBD**: JTBD-001
**Persona**: developer

## Description

`/wr-itil:transition-problem` validates the destination against a three-row table — `.open.md → known-error`, `.known-error.md → verifying`, `.verifying.md → close` — and its Step 3 says "any other pairing | — | no — emit an error and stop". A ticket in `closed/` therefore has no reachable destination: the skill refuses every argument.

The gap is not theoretical, because closure notes actively prescribe the refused command. P402's `## Verified & Closed` section, written by the closing session, reads:

> **Recovery**: reversible via `/wr-itil:transition-problem 402 known-error` or `git revert`.

Reopening P402 on 2026-08-20 could not use that command. The transition was done by hand instead: `git mv closed/ → known-error/`, an Edit to the Status field, the `## Reopened` section, the README WSJF row insertion, the P134 last-reviewed rotation, and the ADR-014 commit — every step that the skill exists to make reliable, performed from memory.

`/wr-itil:manage-problem`'s ownership boundary says the bare-`<NNN>` update flow stays with it, so manage-problem is the other candidate home. Either way, one of the two skills should own the direction; today neither does, and the closure-note text points at the one that refuses.

## Symptoms

- `/wr-itil:transition-problem <NNN> known-error` on a `closed/` ticket errors and stops.
- Closure notes generated by the transition flow cite that exact command as the recovery path.
- Reopens are performed by hand, so the staging-trap re-stage (P057), README refresh (P062) and commit-grain (ADR-014) disciplines are unenforced on that path.

## Workaround

Perform the reopen by hand and carry the skill's discipline manually: `git mv` the file from `closed/` to `known-error/`, Edit the `**Status**` field, append a `## Reopened` section stating what the prior verification missed, re-stage after the Edit, insert the WSJF row into `docs/problems/README.md`, rotate line 3 into `README-history.md`, and commit through the risk gate.

## Impact Assessment

- **Who is affected**: anyone reopening a wrongly-closed ticket — this repo and adopters, since both skills ship in `@windyroad/itil`.
- **Frequency**: once per reopen. Two reopen-shaped events are on record in this repo's history (the 2026-04-27 P124 regression flip-back, and P402 on 2026-08-20).
- **Severity**: no data loss; the manual path works. The cost is that lifecycle discipline becomes memory-dependent exactly when a prior closure has already proven fallible.
- **Analytics**: 236 tickets currently in `docs/problems/closed/`.

## Root Cause Analysis

### Preliminary Hypothesis

The lifecycle was modelled as a forward-only pipeline. `Closed` reads as terminal, so no backward direction was specified — but ADR-022 treats closure as a *claim* about a fix, and claims can be falsified by later evidence. The closure-note template compounds it by asserting a recovery command without a test that the command accepts that transition.

### Investigation Tasks

- [ ] Decide the owning skill: a fourth row in `transition-problem`'s table (`closed → known-error`), or the reopen flow on `manage-problem`'s bare-`<NNN>` update path
- [ ] Specify the pre-flight for the direction — at minimum, require a stated reason for the reopen, so the ticket records what the prior verification missed rather than silently flipping state
- [ ] Decide whether reopening should mark the superseded `## Verified & Closed` / `## Fix Released` sections automatically, since a reopened ticket asserting a shipped fix is self-contradicting (done by hand on P402)
- [ ] Fix the closure-note template so it stops prescribing a command that refuses
- [ ] Create a reproduction test: a `closed/` ticket plus a reopen argument must transition, not error
