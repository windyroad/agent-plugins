## What You Need to Know

### The shipped I13 propose-fix gate directs the SUPERSEDED RFC form — auto-created fix-time RFCs get rejected by the architect (2026-07-03)

When you work an RFC-less Known Error, `wr-itil-check-fix-rfc-trace` emits `no-rfc-trace` and the manage-problem/work-problems I13 SKILL text tells you to auto-create a fix-time RFC (via `capture-rfc --fix-time`) with authored `## Scope` + `## Tasks`. **That directive is stale.** ADR-073 was rewritten and re-confirmed 2026-06-29: an RFC is now **comprised of stories in a user story map** (ADR-060/089/090), NOT a `Scope`+`Tasks` prose blob; "auto-create at fix-time and never block" is **rejected**; and the P399 `capture-rfc --fix-time` mechanism is **held, not shipped, pending rework**. ADR-073 itself flags the lockstep gap: ADR-072 (gate placement, confirmed) + ADR-060's I13 invariant (accepted) + the `wr-itil-check-fix-rfc-trace` gate code still encode the rejected stance and **require a matching amendment that has not landed**. Consequence: the architect gate will (correctly) reject a `stories: []` Scope+Tasks RFC as ISSUES FOUND, and ADR-089's `wr-itil-check-rfc-has-stories` blocks such an RFC from reaching `accepted` anyway. Until the lockstep amendment ships, an AFK iter hitting this path cannot cleanly auto-create the RFC — record the finding on the ticket and queue the reconciliation rather than forcing the superseded form. Witnessed 2026-07-03 working P357 (RFC-040 attempt). <!-- signal-score: 2 | last-classified: 2026-07-03 | first-written: 2026-07-03 -->

### WSJF is computed ONLY at README render time — transitions silently leave the cache stale (2026-06-28)

Problem tickets carry `**Priority**:` (Impact×Likelihood) and `**Effort**:` lines but NO `**WSJF**:` line — WSJF is derived at render time in `docs/problems/README.md` by `/wr-itil:review-problems` Step 5. So a status transition (`/wr-itil:transition-problem`, work-iter O→KE) that changes the WSJF multiplier (Open 1.0 → Known Error 2.0) does NOT recompute the README's WSJF column. The ranking silently shows the Open-era value until the next `review-problems` re-render. Witnessed 2026-06-28: 11 KE-cluster tickets transitioned O→KE on 2026-06-16 still showed WSJF 1.5 (should be 3.0); P390 showed 6.0 (should be 12.0 — Sev-12 KE); recent captures showed 0.75 placeholders. `reconcile-readme.sh` does NOT catch this — it checks section *membership*, not WSJF *arithmetic/sort order*. So the WSJF table can be badly mis-sorted (recent captures prepended above higher-WSJF rows) and reconcile still exits 0. Implication: trust the README WSJF ranking only right after a `review-problems` pass; a mid-cycle backlog will lag reality. Candidate fix space (P389-adjacent): have the transition skills refresh WSJF in the same commit, or add a render-correctness check to reconcile. <!-- signal-score: 2 | last-classified: 2026-06-28 | first-written: 2026-06-28 -->
