# Architect Gate Marker Mechanics

How the `wr-architect:agent` completion reaches the shared marker writer and which verdict shapes carry authority. The P099 Tier 3 budget rotation split this file out of [`agent-hook-gate-quirks.md`](./agent-hook-gate-quirks.md) on 2026-07-26.

Sibling files: [`agent-hook-gate-quirks.md`](./agent-hook-gate-quirks.md) (other gate quirks), [`hooks-and-gates.md`](./hooks-and-gates.md) (gate inventory), [`agent-interaction-patterns.md`](./agent-interaction-patterns.md) (broader interaction discipline).

## What You Need to Know

- **The accepted verdict shapes and the caller-bound completion path** (what actually writes the marker, rather than what stops it being written) are in [`architect-gate-marker-mechanics-archive.md`](./architect-gate-marker-mechanics-archive.md), rotated there 2026-09-19 under the Tier 3 budget. Read it when a marker's absence is not explained by the facets below.

- **The verdict heading must be TITLE CASE — put `**Architecture Review: PASS**` in the spawn prompt verbatim.** An all-caps heading matches neither accepted shape, so the verdict parses empty, no marker is written, and the next gated edit reads as though no review happened. Re-spawning cannot fix it. The full account, including the six spawns it cost on 2026-09-04, is in [`architect-gate-marker-mechanics-archive.md`](./architect-gate-marker-mechanics-archive.md), rotated there 2026-09-19 under the Tier 3 budget. <!-- signal-score: 4 | last-classified: 2026-09-19 | first-written: 2026-09-04 -->
- **A gate that only unlocks on PASS cannot be cleared for a file that does not exist yet — stage the draft outside the gated path and point the reviewer at it.** The architect and JTBD gates write a marker only on a clean PASS verdict; ISSUES FOUND writes nothing, so the edit stays blocked. That is fine while the reviewer can read what you propose, but a NEW file under a gated path (`docs/decisions/`, `docs/stories/`) is a deadlock: you cannot write it without a marker, and a pre-edit prose description of it is what the reviewers keep returning ISSUES FOUND on, because they are judging a summary rather than the artefact. Write the full draft into the session scratchpad, give the reviewer its absolute path, say plainly that it lands at the gated path verbatim once passed, then copy it across on PASS. Both reviewers read files outside the repo without complaint, and their findings get sharply more specific once they are reading real text — on 2026-09-19 the JTBD reviewer's pre-edit pass raised five findings against a described ADR and its post-draft pass discharged all five by citing line numbers. Budget for two rounds per gated new file: one on the description to shape it, one on the draft to clear it.

- **A correctly-formatted PASS from a fresh foreground spawn can still leave no marker — and the deny message's own recovery clears it in one go.** On 2026-09-19 a fresh `wr-architect:agent`, spawned in the foreground with `run_in_background: false`, returned the exact literal `**Architecture Review: PASS**`. The next edit under `packages/…/eval/` was refused with "No architect review marker found for this session", and `/tmp` held an `architect-announced-<SID>` for the session but no `architect-reviewed-<SID>`. So the verdict-format facet was not in play — this is the SID-binding half of P468 reproducing on a plain foreground spawn, with no `SendMessage` resume (P400) and no Codex transport involved. What is new is the recovery: `touch /tmp/architect-reviewed-$SID && rm -f /tmp/architect-reviewed-$SID.hash`, with `$SID` taken from the `architect-announced-*` basename, was accepted and unblocked the edit on the first attempt — not refused, and not needing the two-candidate-UUID dance the earlier witness paid. Hold a genuine PASS first; the assertion is a transcription of a review that happened, never a substitute for one. **Second witness later the same day narrows the trigger: dispatching two reviewers in ONE assistant message.** The architect and JTBD agents were sent as two `Agent` calls in a single message, both foreground, both returning their exact literal verdicts — and only the JTBD marker landed. `/tmp` held `jtbd-reviewed-<SID>` and `jtbd-plan-reviewed-<SID>` for the session but, for architect, only `architect-announced-<SID>`. So the marker writer appears to service one Agent completion per message. Send gate reviewers whose markers you need in separate messages, or expect to hand-assert one of them. The deny message's recovery worked on the first attempt again.
