# Architect Gate Marker Mechanics

How the `wr-architect:agent` PostToolUse marker is written, why it silently is not written, and the sanctioned recovery when you already hold an approving review. Split out of [`agent-hook-gate-quirks.md`](./agent-hook-gate-quirks.md) on 2026-07-26 per the P099 Tier 3 budget rotation — the entry had grown to stand alone.

Sibling files: [`agent-hook-gate-quirks.md`](./agent-hook-gate-quirks.md) (other gate quirks), [`hooks-and-gates.md`](./hooks-and-gates.md) (gate inventory), [`agent-interaction-patterns.md`](./agent-interaction-patterns.md) (broader interaction discipline).

## What Will Surprise You

- **PostToolUse `architect-mark-reviewed.sh` writes the gate marker ONLY on a fresh `Agent` tool call — NEVER on a `SendMessage` resume of an existing architect agent.** Two compounding quirks: (1) the hook parses the verdict by anchored grep on the `**Architecture Review: PASS**` / `**ISSUES FOUND**` heading — an `ISSUES FOUND` first verdict writes no marker (FAIL branch); (2) more importantly, the hook is a `PostToolUse:Agent` hook, so resuming the architect via `SendMessage` to upgrade ISSUES→PASS does NOT fire it at all — even a clean `**Architecture Review: PASS**` from the resumed agent leaves the marker unwritten. So the "re-invoke OR SendMessage asking for a PASS heading" workaround is HALF WRONG: SendMessage-resume will not set the marker. Recovery after a genuine approving PASS (verified 2026-06-28, P399 iter): either (a) fresh-spawn a new `wr-architect:agent` whose output leads with `**Architecture Review: PASS**` (fires the PostToolUse, writes marker+hash), or (b) the sanctioned manual assertion — `touch /tmp/architect-reviewed-$SID && rm -f /tmp/architect-reviewed-$SID.hash` (marker-present + no-hash → `architect-gate.sh` allows AND skips the docs/decisions drift re-check, immunising subsequent same-session edits). Use (b) when you already hold a genuine PASS and want to avoid a wasteful full re-review.
  **Get the SID from the runtime-sid marker's CONTENTS, not from a marker basename (verified 2026-07-26, P429 iter).** The hook's own deny message says "SID = newest `architect-plan-reviewed-*` / `architect-announced-*` basename" — that is wrong often enough to burn several turns: those markers accumulate one per *past* session, and the newest is frequently not the current one. Two manual assertions against basename-derived UUIDs both re-blocked before the third attempt worked. The reliable source is `cat "$(ls -t /tmp/itil-runtime-sid-$(whoami)-*.current | head -1)"` — the itil runtime-sid marker whose *contents* are the live `session_id` the PreToolUse hook reads from its stdin payload. Cross-check: it matches the basename of your session's transcript directory under `~/.claude/projects/<project-slug>/`. Same root cause as the create-gate SID-discovery problem P124/P260 solved for `wr-itil-mark-create-gate` (which enumerates *every* candidate SID precisely because no single-SID guess is reliable) — the architect marker has no equivalent enumerating shim, so the manual path has to pick correctly.
  **Also note the verdict-heading grep is literal.** An architect that leads with `## Architecture Review: APPROVED` — a natural and entirely approving phrasing — does not match the `**Architecture Review: PASS**` anchor, so no marker is written and the edit stays blocked even though the review passed. Observed 2026-07-26. **`## Architecture Review: PASS WITH NOTES` fails the same way** (observed 2026-07-26, P430 iter) — and this is the common case, not an edge case: a thorough architect that approves the substance while listing non-blocking notes naturally reaches for that heading, so a genuinely approving review routinely leaves the gate shut. Recovery path (b) applies.
