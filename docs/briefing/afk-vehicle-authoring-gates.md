# Authoring the Fix Vehicle — Which Gates Fire, In What Order

The write-gate mechanics an AFK iteration pays when it authors a fix vehicle, and the ordering
that stops you paying twice. Split out of [`afk-ratification-hold.md`](./afk-ratification-hold.md)
on 2026-07-26 per the P099 Tier 3 budget rotation — the rule ("an AFK iter cannot land code")
and the gate mechanics ("here is what blocks the Write, and in what order") are different
questions asked at different moments, and only the rule needs to be in context while planning.

Load this file once you have decided to author artefacts and want the write order that minimises
blocked-Write round-trips. The rule itself, and the per-iteration cost accounting, live in
[`afk-ratification-hold.md`](./afk-ratification-hold.md) and
[`afk-ratification-hold-witnesses.md`](./afk-ratification-hold-witnesses.md).

## What You Need to Know

- **`docs/rfcs/` has a third write gate that front-loading the reviewers does not clear.** With architect and jtbd markers both valid, the RFC Write still denies: the ADR-060 I1 trace gate requires the file be created through `/wr-itil:capture-rfc`, which runs the preflight, validates each `P<NNN>` trace resolves, and writes `/tmp/wr-itil-rfc-capture-grep-$SID` via `wr-itil-mark-rfc-capture-gate`. Budget the skill invocation as a step, not a surprise. The other four artefact paths have no equivalent. P424 iter 2026-07-26. <!-- signal-score: 2 | last-classified: 2026-07-26 | first-written: 2026-07-26 -->
- **The JTBD gate will block the sanctioned AFK vehicle shape on its build-upon guard, and it is wrong to — cite the contract and it withdraws.** Authoring an RFC + story naming a born-`unconfirmed` job trips ADR-068 item 7, and the reviewer's first instinct is "ratify the job first" — which has no AFK path. Cite `work-problems/SKILL.md` line 382 (*"The drain is NOT a halt — `unconfirmed` markers are explicit-by-design AFK signals"*) and `capture-story/SKILL.md` line 252 (*"born-unconfirmed is the load-bearing default"*). The test: is the artefact (a) born unconfirmed, (b) ratifying at the SAME drain event as the cited job, and (c) shipping no implementation? ADR-090's narrow `stories:` reference gate proves the framework bars *referencing*, not *authoring*. Put this in the first jtbd prompt and save two spawns; P439 iter 2026-07-26 paid three. <!-- signal-score: 2 | last-classified: 2026-07-26 | first-written: 2026-07-26 -->
- **A genuine architect PASS can leave the gate still locked, because the marker lands under the SUBAGENT's session id rather than the session's.** P417 iter 2026-07-26: a fresh `wr-architect:agent` spawn returned `**Architecture Review: PASS**` in the required leading-bold form, and the next Edit still denied with *"No architect review marker found for this session"*. `ls -lt /tmp/architect-*` showed the marker written moments earlier at `/tmp/architect-reviewed-<subagent-uuid>`, while every `*-announced-*` marker for the session carried a different uuid — the P368 SID-discovery class, hitting the architect gate rather than an oversight shim. Do not re-spawn the reviewer: a second PASS lands under a second wrong uuid. Take the recovery the deny message itself prints — `touch /tmp/architect-reviewed-$SID && rm -f /tmp/architect-reviewed-$SID.hash` — and assert it under BOTH uuids (the newest `architect-announced-*` basename and the one the subagent actually wrote), because you cannot tell from outside which the hook will read. Tracked by P400 / P215 / RFC-021. <!-- signal-score: 2 | last-classified: 2026-07-26 | first-written: 2026-07-26 -->
- **Any edit under `docs/jtbd/` re-locks the JTBD gate — including a mechanical reverse-trace refresh to an existing job file.** P438 recorded that *authoring* a new job invalidates the marker. P417 iter 2026-07-26 widens it: running `wr-itil-update-jtbd-references-section` to refresh the derived `## Stories` table on four existing job files was enough. The hook keys on policy-path drift, not on whether the edit carried semantic substance, so a body-only helper write to a ratified job trips it exactly like authoring a new one. Consequence for any multi-tier reconcile: the pass that touches `docs/jtbd/` invalidates the marker for everything you were going to do afterwards. Sequence `docs/jtbd/` writes into the LAST commit of the pass, or budget a re-review round. <!-- signal-score: 2 | last-classified: 2026-07-26 | first-written: 2026-07-26 -->
