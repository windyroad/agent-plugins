# Authoring the Fix Vehicle — Which Gates Fire, In What Order

The write-gate mechanics an AFK iteration pays when it authors a fix vehicle, and the ordering
that stops you paying twice. Split out of [`afk-ratification-hold.md`](./afk-ratification-hold.md)
on 2026-07-26 per the P099 Tier 3 budget rotation — the rule ("an AFK iter cannot land code")
and the gate mechanics ("here is what blocks the Write, and in what order") are different
questions asked at different moments, and only the rule needs to be in context while planning.

Load this file once you have decided to author artefacts and want the write order that minimises
blocked-Write round-trips. The rule itself, and the per-iteration cost accounting, live in
[`afk-ratification-hold.md`](./afk-ratification-hold.md) and
[`afk-ratification-hold-witnesses.md`](./afk-ratification-hold-witnesses.md).

## What You Need to Know

- **If the architect prescribes an ADR capture mid-loop, make it the LAST gated write of the iteration — the guard re-flags the loop's own prescribed ADR and there is no AFK way to clear it.** `capture-adr` is *mandated* to birth ADRs `human-oversight: unconfirmed` (ADR-066 / P348; the marker-discipline hook denies `confirmed` without a real confirm event). The `[Unratified Dependency]` check is a pure function of the cited ADR's own frontmatter with no provenance input, so it cannot tell "prescribed by this same reviewer three turns ago" from "stale decision someone is quietly building on" — and the only clearing action it names, `/wr-architect:review-decisions`, is an `AskUserQuestion` drain the ADR-044 AFK carve-out forbids mid-loop. So the framework requires the artefact the guard blocks, with no reachable escape. **Do not chase the drift hash for this**: `architect-refresh-hash.sh` already refreshes on allowed writes to `docs/decisions/`, and `_substance_hash_path` excludes `README.md`, so no marker invalidation is involved — *any* fresh reviewer spawn later in the session re-flags, including one fired by a routine TTL slide. Sequencing the capture last costs nothing, because dependent code is held for ratification anyway under ADR-096. Tracked as P425 (Known Error) with four candidate carve-outs recorded and the pick queued; **the same guard is duplicated on the JTBD gate via RFC-011**, so the deadlock is live on both surfaces until a fix lands on both. <!-- signal-score: -2 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
- **`docs/rfcs/` has a third write gate that front-loading the reviewers does not clear.** With architect and jtbd markers both valid, the RFC Write still denies: the ADR-060 I1 trace gate requires the file be created through `/wr-itil:capture-rfc`, which runs the preflight, validates each `P<NNN>` trace resolves, and writes `/tmp/wr-itil-rfc-capture-grep-$SID` via `wr-itil-mark-rfc-capture-gate`. Budget the skill invocation as a step, not a surprise. P424 iter 2026-07-26; re-hit P434 2026-07-26. <!-- signal-score: 1 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
- **The JTBD gate will block the sanctioned AFK vehicle shape on its build-upon guard, and it is wrong to — cite the contract and it withdraws.** Authoring an RFC + story naming a born-`unconfirmed` job trips ADR-068 item 7, and the reviewer's first instinct is "ratify the job first" — which has no AFK path. Cite `work-problems/SKILL.md` line 382 (*"The drain is NOT a halt — `unconfirmed` markers are explicit-by-design AFK signals"*) and `capture-story/SKILL.md` line 252 (*"born-unconfirmed is the load-bearing default"*). The test: is the artefact (a) born unconfirmed, (b) ratifying at the SAME drain event as the cited job, and (c) shipping no implementation? ADR-090's narrow `stories:` reference gate proves the framework bars *referencing*, not *authoring*. Put this in the first jtbd prompt and save two spawns; P439 iter 2026-07-26 paid three; P434 2026-07-26 pre-empted it in the first prompt and the guard never fired — the reviewer noted it did not even reach that edge case. <!-- signal-score: 1 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
- **Any edit under `docs/jtbd/` re-locks the JTBD gate — including a mechanical reverse-trace refresh to an existing job file.** P438 recorded that *authoring* a new job invalidates the marker. P417 iter 2026-07-26 widens it: running `wr-itil-update-jtbd-references-section` to refresh the derived `## Stories` table on four existing job files was enough. The hook keys on policy-path drift, not on whether the edit carried semantic substance, so a body-only helper write to a ratified job trips it exactly like authoring a new one. Consequence for any multi-tier reconcile: the pass that touches `docs/jtbd/` invalidates the marker for everything you were going to do afterwards. Sequence `docs/jtbd/` writes into the LAST commit of the pass, or budget a re-review round. P434 2026-07-26 followed this and paid no re-review. <!-- signal-score: 1 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
