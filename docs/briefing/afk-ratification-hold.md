## What You Need to Know

- **Approval is the story MAP's, not the story's (ADR-103, 2026-08-07) — the full rule now lives in [`afk-approval-is-the-story-map.md`](./afk-approval-is-the-story-map.md).** Read it before planning any AFK iteration that intends to ship a code change. <!-- signal-score: 4 | last-classified: 2026-09-19 | first-written: 2026-07-26 -->
- **The same commit closed the inverse hole (P465).** `itil-no-implement-draft-gate` now denies a commit whose `Refs: STORY-NNN` trailer names an `accepted`/`in-progress` story that is **not approved** — unconditionally, for every adopter, no config. Before this, the ADR-096 claim that no unratified story could be implemented was held closed by decision alone and was open in code. Under ADR-103 the gate's only test is `story_is_approved`: every map in the story's `story-maps:` field must be ratified. **A story edit can never trip it** — stories carry no fingerprint, so editing a story body, ticking a criterion or advancing status changes nothing. Only a SUBSTANCE edit to the MAP re-opens approval, and the recovery is to re-ratify the map, never the story. <!-- signal-score: 4 | last-classified: 2026-08-30 | first-written: 2026-07-26 -->
- **The fix vehicle is a release ROW, not a document (ADR-119, ratified 2026-08-21).** A fix proposal creates no new file under `docs/rfcs/`, and legacy RFC documents take no authored edits either — so the P371 "wire the trace edge into the existing RFC" move is dead with the tier. Draw a release row on a story map instead, allocating its `rfc` identity by scanning row identities across **all maps plus git history** — never `max()` over `docs/rfcs/`, which returns an id a row already owns. Drawing the row and adding its card leave the map's fingerprint intact, verified. The shipped `manage-problem` I13 gate and `wr-itil-check-fix-rfc-trace` still teach the document path and will route you into the barred action; only the architect gate catches it (P508). <!-- signal-score: 3 | last-classified: 2026-08-30 | first-written: 2026-08-21 -->
- **The ratification question an iter queues is NOT durable — the queue rotates and drops entries unanswered.** The hold rule's whole premise is that an iter that cannot land a fix authors the vehicle and *queues* the ratification for the next interactive drain, so the held work stays reachable. It does not. Witnessed 2026-09-19 on P429: two questions (an ADR-amendment ratification and a regression-guard design pick) were queued on 2026-07-26 and are simply gone — `.afk-run-state/outstanding-questions.jsonl` now holds three unrelated entries, and neither question was ever answered or back-written to the ticket. Nearly two months of selections re-derived the same dead end. Consequence: a ticket whose Investigation Tasks are fully held has exactly ONE live re-entry path — its own WSJF rank — and each selection can only re-confirm the block while burning a top-of-queue iteration slot. So (a) when an iter queues a question, also write it into the ticket body, which is the only surface that survives; (b) do not read a held ticket's "queued for the next drain" annotation as evidence the question is still live — check the queue file; (c) a Tier-1 ticket held on a user answer is a ranking problem as much as a ratification one. Distinct from the older accumulates-without-a-drain entry in [`agent-hook-gate-quirks-archive.md`](./agent-hook-gate-quirks-archive.md) — that was the queue growing unread; this is the queue losing entries.
