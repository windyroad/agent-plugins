## What You Need to Know

- **THE WALL IS BROKEN — approval is the story MAP's (2026-08-07).** ADR-103 retired the ADR-101 carve-out entirely: `wr-itil-check-afk-accept-eligible`, the `afk_accept_pure_decomposition` config key and the `afk-accept:` story field are GONE — do not reach for them. A story is approved when the story map it sits on is ratified. A story carries NO oversight field at all — approval is derived from its `story-maps:` field, and the marker writer refuses a story path. Ratifying a map approves every story on it, including stories added later, so an AFK loop that needs to land a story on an already-ratified map may accept and implement it with no further ratification event. Adding a release row or a story to a row no longer drifts a map's fingerprint. What still needs a human — all four legs, per ADR-103 line 47: a NEW map, a NEW activity column, a change to a map's own prose or traces, **or a NEW ADR**. The ADR leg is the one this entry used to omit and the one that most often fires: if the fix changes substance recorded in a ratified decision, ADR-116 allows change only by supersession, so the proposal needs a new ADR and implementation is refused however well-approved the story is. **Ratification is a MARKER, not a directory** — on 2026-08-21 all five maps sat in `docs/story-maps/draft/` and every one carried `"humanOversight": "confirmed"` with a matching hash. Reading the directory says nothing; read the marker. Test with `story_is_approved` for a story and `is_story_map_ratified` for a map; the story tier has no marker to read. **Everything below still holds for a story whose map is not ratified.** <!-- signal-score: 8 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
- **The same commit closed the inverse hole (P465).** `itil-no-implement-draft-gate` now denies a commit whose `Refs: STORY-NNN` trailer names an `accepted`/`in-progress` story that is **not approved** — unconditionally, for every adopter, no config. Before this, the ADR-096 claim that no unratified story could be implemented was held closed by decision alone and was open in code. Under ADR-103 the gate's only test is `story_is_approved`: every map in the story's `story-maps:` field must be ratified. **A story edit can never trip it** — stories carry no fingerprint, so editing a story body, ticking a criterion or advancing status changes nothing. Only a SUBSTANCE edit to the MAP re-opens approval, and the recovery is to re-ratify the map, never the story. <!-- signal-score: 4 | last-classified: 2026-08-29 | first-written: 2026-07-26 -->
- **The fix vehicle is a release ROW, not a document (ADR-119, ratified 2026-08-21).** A fix proposal creates no new file under `docs/rfcs/`, and legacy RFC documents take no authored edits either — so the P371 "wire the trace edge into the existing RFC" move is dead with the tier. Draw a release row on a story map instead, allocating its `rfc` identity by scanning row identities across **all maps plus git history** — never `max()` over `docs/rfcs/`, which returns an id a row already owns. Drawing the row and adding its card leave the map's fingerprint intact, verified. The shipped `manage-problem` I13 gate and `wr-itil-check-fix-rfc-trace` still teach the document path and will route you into the barred action; only the architect gate catches it (P508). <!-- signal-score: 1 | last-classified: 2026-08-29 | first-written: 2026-08-21 -->
