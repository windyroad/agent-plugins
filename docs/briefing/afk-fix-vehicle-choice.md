# Choosing and shaping the fix vehicle

Split out of [`afk-ratification-hold.md`](./afk-ratification-hold.md) on 2026-09-19 when that file crossed the Tier 3 budget. The hold rule — why an AFK iter authors a vehicle but cannot land the fix — stays there. This file is the narrower question it leaves open: once the I13 gate says a fix needs a vehicle, *which* vehicle, and *what shape* it takes.

## What You Need to Know

- **The fix vehicle is a release ROW, not a document (ADR-119, ratified 2026-08-21).** A fix proposal creates no new file under `docs/rfcs/`, and legacy RFC documents take no authored edits either — so the P371 "wire the trace edge into the existing RFC" move is dead with the tier. Draw a release row on a story map instead, allocating its `rfc` identity by scanning row identities across **all maps plus git history** — never `max()` over `docs/rfcs/`, which returns an id a row already owns. Drawing the row and adding its card leave the map's fingerprint intact, verified. Both surfaces have since been corrected and now teach the row path: on 2026-09-19 `wr-itil-check-fix-rfc-trace` returned *"Draw one on a story map that already covers this journey, give it at least one story card … Give the row the identity RFC-097"*, and `manage-problem`'s I13 section reads *"A fix proposal is a release row on a story map. It is never a new document under `docs/rfcs/`"*. P508 (the ticket for the old document-path directive) is still at Known Error, so the correction has not been verified through its lifecycle — but the barred-action routing this entry used to warn about was not observed. <!-- signal-score: 3 | last-classified: 2026-08-30 | first-written: 2026-08-21 -->

- **When the I13 gate says nothing proposes a fix, the choice between wiring an existing row and drawing a new one has a hard tiebreaker: a row renders delivered when its stories ship (ADR-107).** Attaching new, undone scope to a row whose driver problem has already reached `verifying` holds that row open past its actual delivery and muddies the verification it is waiting on — so a *new* row is correct even when an existing one looks thematically adjacent. The I13 prose only offers the softer "composes with / Related background is not a fix-vehicle signal" test, which is easy to talk yourself past when the adjacent row's stories cover part of your scope. Witnessed P432 2026-09-19: RFC-061 "The reporter is kept in the loop end to end" carried STORY-028, whose acceptance criteria are a strict subset of what P432 needed — and it was still the wrong row, because P080 (its driver) sits at `verifying`. The architect supplied the ADR-107 reasoning; the I13 signal test alone would have been a coin flip. Say the relationship out loud in the new story's body when the rows overlap ("this generalises STORY-028; RFC-061 keeps it as the single-channel instance"), or the map promises the same outcome twice with nothing telling a reader which row still owes it.

- **A clean I13 trace means a vehicle exists, not that a card covers what you are about to build — check card coverage per reported face BEFORE the design pass.** The predicate answers "does a fix vehicle exist for this problem?"; what the next step needs is "does a card on that row cover this scope?" Those come apart on any ticket with more than one reported face. Witnessed P435 2026-09-19: the ticket carries two inbound reports (a push gate over-firing, an external-comms gate under-firing), traces RFC-062, and that row carries a card for the over-fire face only — the other has no card and no story file anywhere, which the surviving story's own Notes say out loud (*"This story is the over-fire face"*). The iteration read the clean trace, designed a fix for both halves, and learned of the gap from the architect, after the design pass was spent. There is no recovery inside an unattended run: drawing the missing card is a capture skill, and capture skills are constrained out. Read the row's cards against the `**Origin**` line's issue list first — it costs one look and saves the pass. Ticketed as P550.
