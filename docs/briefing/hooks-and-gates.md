# Hooks and Gates

Learnings about PreToolUse/PostToolUse gate behaviour, markers, and expiry.

## What You Need to Know

- **`RISK-POLICY.md` is edit-gated behind `/wr-risk-scorer:update-policy`, which MANDATES `AskUserQuestion` (its step 6 "do not proceed until you have received answers") — so an AFK iter CANNOT add or amend a policy section, even an additive one.** This bites when a shippable change is coupled to a new policy class for ADR-026 grounding (e.g. P384's new external-comms credibility axis needs an `## Outbound Credibility / Self-Own` policy section to cite verbatim). The lazy resolution: ship the agent half (agents read their class list from `RISK-POLICY.md` at runtime, so a new axis degrades to dormant where the section is absent — no home-repo regression — and activates for any adopter who authored the section), and queue the home-repo policy-section edit for an interactive `/wr-risk-scorer:update-policy` pass. Do NOT try to drive update-policy AFK or bypass the policy edit-gate. (2026-06-27, P384 iter.) <!-- signal-score: 2 | last-classified: 2026-06-27 | first-written: 2026-06-27 -->
- **Gate-reviewer marker hooks fire ONLY on synchronous Agent-tool completion — a SendMessage-resumed reviewer writes NO marker.** If a gate reviewer (architect/jtbd/etc.) returns ISSUES FOUND (no marker — correct) and you continue it via SendMessage with the issues resolved, the re-verdict PASS arrives as a background task-notification and the PostToolUse mark hook never fires: the edit gate re-blocks despite a genuine PASS on record. Recovery that works: fold the issue resolutions into the proposal and dispatch a FRESH synchronous Agent call (`run_in_background: false`) — its PASS persists the marker. Cost of the wrong path: one wasted resume + a full fresh re-review (~70k subagent tokens, P324 iter 2026-07-05). RESUME variant of P402's launch-variant class; tracked as P418. <!-- signal-score: 2 | last-classified: 2026-07-05 | first-written: 2026-07-05 -->
- **A FRESH architect spawn returning PASS still writes no marker if its verdict line is a markdown heading (`## Architecture Review: PASS`) rather than bold — and the deny message's own recovery names the wrong SID source.** Distinct from the SendMessage-resume miss above: the spawn was synchronous and fresh, the PASS unambiguous, and the gated Write was still denied. The deny text says to derive the SID from the newest `architect-plan-reviewed-*` / `architect-announced-*` basename; the gate actually reads the `session_id` on the Write's stdin, which can be a different UUID recorded in `/tmp/itil-runtime-sid-<user>-<n>.current`. Asserting under the announce-marker UUID alone re-blocks. Recovery that works: read every `/tmp/itil-runtime-sid-*.current` value and `touch /tmp/architect-reviewed-<sid>` + `rm -f` its `.hash` sibling for each recent candidate — same candidate-set discipline the create-gate marker uses per ADR-050 Option C. Tracked as P468; the ISSUES-FOUND-substring precedent is P181. (2026-07-26, P438 iter.) <!-- signal-score: 2 | last-classified: 2026-07-26 | first-written: 2026-07-26 -->
- **The style-guide and voice-tone reviewers are spawned read-only, so they cannot write the verdict file their own contract names — and they will ask you to write it for them.** Both closed their reviews in the P438 iter reporting they had no Bash and could not `printf` to `/tmp/style-guide-verdict` / `/tmp/voice-tone-verdict`. Do not forge the verdict on their behalf: a caller-written verdict is not an independent review, and if the file turns out to be load-bearing that is the hollow-marker class (P348). Treat the returned verdict text as the authority and let the PostToolUse mark hook do its job. Tracked as P469 — which mechanism is actually live for each gate is its first investigation task.
