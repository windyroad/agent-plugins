## Rotated 2026-06-08 (Tier-3 split-by-date — older 2026-05-26 entries)

### Known Error semantics: root cause + workaround, NOT "fix ready" — the RFC/fix comes AFTER (2026-05-26)

A problem reaches **Known Error** when its **root cause is identified AND a workaround is documented** — there is no fix and no RFC yet (ADR-022 is the authority; it says Known Error = "root cause confirmed, fix not yet shipped"). Only *after* Known Error do you **propose a fix**, which is what **produces the RFC**. And `Fix Released` is **not** a separate state — releasing the fix **is** the `Known Error → Verifying` transition. So the lifecycle is `Open → Known Error → Verifying → Closed`. Consequence for any fix-time gate: the RFC is required at the **propose-fix step on a Known Error**, NOT at `Open → Known Error` (a problem gets to Known Error with no fix). I (and RFC-005 F1 → ADR-072) got this wrong — placed the gate at `Open → Known Error` on a "Known Error = fix is real" misreading; the oversight drain caught it, rework = P314. **Cite ADR-022 when reasoning about Known Error / fix-time placement** — the wrong-model placement landed precisely because ADR-022 wasn't referenced.

### "No schema change" ≠ "no ADR" — a direction-extension still needs an amendment (2026-06-22)
When a fix extends a governance contract by adding a *direction* / *consumer* / *branch* — even when it introduces NO new data schema and reuses an existing field — the architect will require recording it as an **amendment to the owning ADR**, not "no ADR at all". Worked example (P363 inbound-origin verdict dispatch): consuming the already-existing `**Origin**: inbound-reported (#NN)` field (ADR-076) to add an inbound verdict leg to `/wr-itil:update-upstream` was *not* a new schema, but it added a new *direction* to ADR-024's wholly-outbound contract — so it needed an ADR-024 amendment (same mechanism as that ADR's P080/P362/Phase-2 amendments), NOT a standalone ADR and NOT zero ADR. The orchestrator's "follows existing schema → no ADR required" framing was half-right (no standalone ADR) and half-wrong (an amendment IS required). Budget the architect round-trip: pre-draft the amendment entry and re-run the architect to get a clean APPROVED marker before editing. Also: amending an existing ADR fires the architect-compendium PostToolUse hook — verify `grep -ac "### ADR-" docs/decisions/README.md` against HEAD after the edit (memory `feedback_compendium_hook_truncates_readme_on_adr_edit`). And per P357/ADR-066, user-ratification of the *mechanism* (e.g. "do option (b)") does NOT ratify the implementation substance (template wording / resolution semantics / new tokens) — queue that to `outstanding_questions` under AFK. <!-- signal-score: -1 | last-classified: 2026-08-30 | first-written: 2026-06-22 -->

### `proposed` ≠ ratified — orthogonal axes; confirm-substance-before-build now has THREE enforcement surfaces (2026-05-27)
`status:` (proposed/accepted) and `human-oversight: confirmed` (ratified) are **orthogonal**. Building on a *ratified-but-`proposed`* ADR is fine; only **unratified** (marker-absent, non-superseded) decisions are the hazard. After the P283 drain, almost every ADR is ratified (2026-05-27: 61/65), so unratified-dependency checks are near-silent. ADR-074 (confirm a decision's SUBSTANCE — the chosen option, not a grain/meta question like "one ADR or two?" — before building dependent work) is now enforced at three surfaces: (1) **record-time** — architect Needs-Direction names the substantive choice (ADR-064); (2) **build-upon @ ITIL propose-fix** — `manage-problem`/`work-problems` run `wr-architect-is-decision-unconfirmed` (RFC-008); (3) **build-upon @ architect-review** — the architect emits `[Unratified Dependency]` ISSUES FOUND when a change/plan cites/implements a marker-less ADR (RFC-010, `@windyroad/architect@0.9.2`). The architect (Read/Glob/Grep, no Bash) does a frontmatter-scoped, superseded-skipping, marker-keyed-NOT-status Grep. New behaviour takes effect on next session restart (P045). See ADR-074, P315/P318.

### WSJF is computed ONLY at README render time — transitions silently leave the cache stale (2026-06-28)

Problem tickets carry `**Priority**:` (Impact×Likelihood) and `**Effort**:` lines but NO `**WSJF**:` line — WSJF is derived at render time in `docs/problems/README.md` by `/wr-itil:review-problems` Step 5. So a status transition (`/wr-itil:transition-problem`, work-iter O→KE) that changes the WSJF multiplier (Open 1.0 → Known Error 2.0) does NOT recompute the README's WSJF column. The ranking silently shows the Open-era value until the next `review-problems` re-render. Witnessed 2026-06-28: 11 KE-cluster tickets transitioned O→KE on 2026-06-16 still showed WSJF 1.5 (should be 3.0); P390 showed 6.0 (should be 12.0 — Sev-12 KE); recent captures showed 0.75 placeholders. `reconcile-readme.sh` does NOT catch this — it checks section *membership*, not WSJF *arithmetic/sort order*. So the WSJF table can be badly mis-sorted (recent captures prepended above higher-WSJF rows) and reconcile still exits 0. Implication: trust the README WSJF ranking only right after a `review-problems` pass; a mid-cycle backlog will lag reality. Candidate fix space (P389-adjacent): have the transition skills refresh WSJF in the same commit, or add a render-correctness check to reconcile. <!-- signal-score: 1 | last-classified: 2026-08-30 | first-written: 2026-06-28 -->

### A ticket blocked by a non-ticket condition stays Open and gets re-selected+skipped forever — Park it (2026-07-04)

The transitive-effort WSJF rule only suppresses a ticket's rank via `**Blocked by**` edges to OTHER tickets, and an upstream in `verifying/`/`closed/`/`parked/` contributes **0** to the closure (carve-out) — so it does NOT suppress. When a ticket is genuinely un-workable but its blocker is (a) an upstream sitting in `verifying/`, or (b) a condition that isn't a ticket at all (an unreconciled/self-contradictory ADR, an architect decision, an un-landed sibling build), **nothing lowers its WSJF** and the AFK loop keeps re-selecting it as top-actionable and skipping it every iter. Witnessed 2026-07-04: P244 selected+skipped **7×** (iters 14–19 + this one) while Open — blocked by P300 (in `verifying/`, contributes 0) + an unreconciled ADR-063 §F9 contract (not a ticket). Fix: **Park it** (Status→Parked, `## Parked` section with reason + un-park trigger, README row moved WSJF-Rankings→Parked). Parked tickets are excluded from ranking + work-selection per ADR-022, so the churn stops; the un-park trigger re-admits it when blockers clear. Don't leave a known-blocked ticket Open just because it has a `Blocked by` edge — check whether that edge actually suppresses the rank. <!-- signal-score: 1 | last-classified: 2026-08-30 | first-written: 2026-07-04 -->

### Reverse-trace helpers and their detector can disagree on column order — trust the helper, not the `STATUS_MISMATCH` line (2026-07-26)

`wr-itil-update-{problem,rfc,jtbd}-references-section` emit `| ID | Title | Status |`. `reconcile-rfcs.sh`'s reverse-trace parser reads field 3 of the pipe-split, which on that shape is the **Title**, so it compares a title string against a lifecycle suffix and reports `STATUS_MISMATCH … claims=<the title text>`. The tell is visible in the output: if `claims=` reads as prose rather than one of `proposed|accepted|in-progress|verifying|closed`, it is the parser, not the data. Verify by checking the table's own status column against the filename suffix before chasing it. `reconcile-stories.sh` parses the same shape correctly, so a clean stories run alongside a noisy RFC run is expected, not contradictory. P417.

### Where you put a table in a governance index changes what the reconciler reports — the detectors bucket by line ranges between `^## ` grep hits (2026-07-26)

`reconcile-rfcs.sh` / `reconcile-readme.sh` / `reconcile-stories.sh` locate their sections with `grep -n '^## <Name>' | head -1`, then scoop every `| <ID> |` cell between one heading's line and the next section's. Two consequences bit P417. **(1) Placement is load-bearing.** Adding 42 rows as a `### Unranked` subsection BETWEEN the rankings table and `## Verification Queue` correctly cleared 42 `MISSING wsjf-rankings` lines; the same rows at the file tail would have bucketed as Closed claims and manufactured 42 spurious `MISMATCH` lines. **(2) A heading inside a fenced ```markdown block still matches**, and `head -1` takes the first hit. `docs/rfcs/README.md` documents the RFC body shape in a fenced block containing `## Closed scope (required when Status reaches closed)`, which prefix-matches `^## Closed` fifty lines above the real section — so `CLOSED_START` lands in the template, the Closed bucket swallows the rankings and queue tables, and `VQ_END` collapses below `VQ_START`, silently disabling the Verification-Queue check entirely. When editing any of these indices: never start a new heading with the string of an existing section heading, and re-run the detector to see which bucket your rows landed in rather than assuming. P417 detector defects queued as fix vehicles.
