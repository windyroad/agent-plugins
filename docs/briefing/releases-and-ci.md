# Releases and CI

Cross-session learnings about push:watch, release:watch, changesets, npm publish, and the GitHub Actions pipeline.

## What You Need to Know

- **`npm pack <relative-path>` is read as a git spec, not a directory.** `npm pack packages/itil` fails with `npm error code EALLOWGIT ... Refusing to fetch "github:packages/itil"` — npm parses the bare `a/b` shape as `github:a/b` before it ever considers the filesystem. `npm pack ./packages/itil` or an absolute path both work. This bites any script that packs workspace packages in a loop: the failure is loud on its own, but a `|| true` anywhere in the pipeline turns it into a survey that reports zero findings for every package. A 13-package leak survey on 2026-09-19 reported all-clean this way; the real count was 846. Same vacuous-pass class as a `grep` over a directory that does not exist. <!-- signal-score: 2 | last-classified: 2026-09-19 | first-written: 2026-09-19 -->

- **The `push:watch` script** in root `package.json` is the sanctioned way to push — it runs `git push` then watches the CI run. The git-push-gate hook blocks bare `git push`. <!-- signal-score: -3 | last-classified: 2026-08-30 | first-written: 2026-08-29 -->
- **Never run `changeset version` locally.** The release pipeline handles versioning. To release: push with `npm run push:watch`, the pipeline creates a release PR, merge it with `npm run release:watch`. <!-- signal-score: -3 | last-classified: 2026-08-30 | first-written: 2026-08-29 -->
- **Post-publish npm verification must tolerate registry propagation, while pre-publish verification must reject immutable version collisions.** A C4 recovery attempted to publish an already-existing `0.2.0`, then the corrected `0.2.1` publish was falsely marked failed because `npm view ... dist-tags.latest` briefly returned `0.1.7`. The shared verifier now checks the version before publish and retries the post-publish `latest` read; commits `cbcda3d1` and `5c33a97d`, release run `33187926547`. <!-- signal-score: -3 | last-classified: 2026-08-30 | first-written: 2026-08-29 -->
- **`npm ci || npm install` in every CI install step means lockfile drift is never reported — it surfaces later, in a job whose name points elsewhere.** The fallback keeps CI moving when the lock is briefly behind, and in doing so discards the only check that the lock is behind at all. On 2026-09-04 `packages/cruise` had been added as a workspace with no entry in `package-lock.json` (`grep -c cruise package-lock.json` returned 0); main was red across at least two runs — including the release merge — with the failing job reported as **Agent-Prose Behavioural Evals**, and the actual message (`npm ci can only install packages when your package.json and package-lock.json are in sync — Missing: @windyroad/cruise@0.4.11`) buried in that job's install step. `npm install --package-lock-only` then `npm ci --dry-run` is the fix and the check. When CI reddens on a job whose subject has nothing to do with the change, read the install step before the job name. P534. <!-- signal-score: 2 | last-classified: 2026-09-04 | first-written: 2026-09-04 -->
- **`wr-risk-scorer-restage-commit` aborts on any commit that carries a rename, if you name the deleted path.** The helper re-adds each supplied path with what behaves as a plain `git add`, which resolves a pathspec against the working tree. A ticket lifecycle transition stages a rename, so the source path is a deletion already in the index and no longer on disk: passing it gives `fatal: pathspec '<old path>' did not match any files` and nothing commits. Naming every path the commit touches is the discipline the helper exists to enforce, and it is exactly what breaks here. Pass the containing directory instead (`-- docs/problems`), which works but re-widens the staging scope this helper narrows — check `git status` first. (P437 iter 2026-09-19; recorded on P454.)
