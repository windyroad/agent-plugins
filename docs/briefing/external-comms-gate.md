# External-Comms Gate

Learnings about the external-comms review gate (changeset / gh-issue / PR-body leak-review) — marker hashing, over-fire, background-agent non-persistence, and BYPASS behaviour. Split from hooks-and-gates.md 2026-07-03 for Tier-3 budget.

## What You Need to Know

- **The external-comms gate marker does NOT persist when the review runs as a *background* `Agent` (P402).** The review returns `EXTERNAL_COMMS_RISK_VERDICT: PASS` but the PostToolUse mark hook never fires for a backgrounded review agent, so the `.changeset/*.md` Write AND the subsequent `git commit` both re-block. **The `BYPASS_RISK_GATE=1` escape is GONE** (P377/RFC-029). The fix is a **synchronous** review: run `/wr-risk-scorer:assess-external-comms`, or pass **`run_in_background: false`** on a direct `Agent` dispatch. **The same non-persistence hits the `wr-risk-scorer:pipeline` commit-score marker** — a backgrounded scorer returns `RISK_SCORES:` and the gate still reports "No commit risk score found". The rule generalises to *every* marker-writing reviewer. `touch`ing the marker by hand is fragile — the gate's SID + key must match exactly, and an empty `CLAUDE_SESSION_ID` (P368 cold path) sends the write to a different dir than the gate reads. Prefer synchronous re-dispatch; where the session offers no synchronous path, use the hand-invoke recipe in the next entry rather than a bare `touch`. **RFC-041 codified the dispatch instruction at four SKILL surfaces + the `risk-gate.sh` DENY on 2026-07-03, and P402 closed on that basis — but P402 REOPENED 2026-08-20 (Known Error).** RFC-041 changed no mechanism; it wrote down a discipline. That works only where the caller both reads the instruction and *can* follow it, and neither holds universally: a caller that dispatches before hitting the DENY never sees it, and **some sessions expose no `run_in_background` parameter on the Agent tool at all** — every dispatch is asynchronous by construction, so "dispatch synchronously" is not an action available to them. Recurrence witnessed 2026-08-10 (addressr `b782a61f`, two full pipeline scores discarded on one commit) and reproduced twice in the 2026-08-20 audit session. **Also do not trust the ticket's stated mechanism**: its title says the hook "does not fire", and the 2026-08-20 evidence does not fit that — two 1-byte files in `.risk-reports/` sit past a guard an empty payload cannot satisfy, and `state-hash` in the risk dir is written by `risk-hash-refresh.sh`, not by the pipeline branch. Three mechanisms remain live (fires-with-empty-payload / fires-and-dies-before-the-marker-writes / never-runs) and P402 now carries tasks to tell them apart. <!-- signal-score: 11 | last-classified: 2026-08-29 | first-written: 2026-07-03 -->
- **When the session gives you no synchronous dispatch, hand-invoke the mark hook with the reviewer's genuine verdict — do not fabricate one, and do not `touch` the marker.** The sanctioned recovery is to run the writer the hook would have run, feeding it the verdict the reviewer actually returned. `risk-score-mark.sh` reads a PostToolUse-shaped payload on stdin; the four fields it needs are `tool_name: "Agent"`, `session_id`, `tool_input.subagent_type` (must contain `risk-scorer.pipeline` — note `.` is a regex wildcard there, so the `wr-risk-scorer:pipeline` colon form matches fine), and `tool_response.content[]` carrying a `{type:"text", text:"RISK_SCORES: commit=N push=N release=N"}` entry. Build it with `python3 -c 'import json; print(json.dumps({...}))' > /tmp/f.json` and pipe: `bash packages/risk-scorer/hooks/risk-score-mark.sh < /tmp/f.json`. It writes the full marker set (`commit`/`push`/`release` + `-born` siblings + `checkout-id` + `state-hash`) under `${TMPDIR}/claude-risk-<SID>/`, so the gate then passes on the real score. Two things this is NOT: it is not `touch`ing a marker (the hook derives checkout-id and state-hash, which a bare touch cannot), and it is not inventing a verdict (the text is the reviewer's own output, pasted). Any tree edit after the mark drifts `state-hash`, so re-score and re-mark.
