# External-Comms Gate

Learnings about the external-comms review gate (changeset / gh-issue / PR-body leak-review) — marker hashing, over-fire, background-agent non-persistence, and BYPASS behaviour. Split from hooks-and-gates.md 2026-07-03 for Tier-3 budget.

## What You Need to Know

- **The external-comms gate marker does NOT persist when the review runs as a *background* `Agent` (P402).** The review returns `EXTERNAL_COMMS_RISK_VERDICT: PASS` but the PostToolUse mark hook never fires for a backgrounded review agent, so the `.changeset/*.md` Write AND the subsequent `git commit` both re-block. **The `BYPASS_RISK_GATE=1` escape is GONE** (P377/RFC-029). The fix is a **synchronous** review: run `/wr-risk-scorer:assess-external-comms`, or pass **`run_in_background: false`** on a direct `Agent` dispatch. **The same non-persistence hits the `wr-risk-scorer:pipeline` commit-score marker** — a backgrounded scorer returns `RISK_SCORES:` and the gate still reports "No commit risk score found". The rule generalises to *every* marker-writing reviewer. `touch`ing the marker by hand is fragile — the gate's SID + key must match exactly, and an empty `CLAUDE_SESSION_ID` (P368 cold path) sends the write to a different dir than the gate reads. Prefer synchronous re-dispatch; where the session offers no synchronous path, use the hand-invoke recipe in the next entry rather than a bare `touch`. **RFC-041 codified the dispatch instruction at four SKILL surfaces + the `risk-gate.sh` DENY on 2026-07-03, and P402 closed on that basis — but P402 REOPENED 2026-08-20 (Known Error).** RFC-041 changed no mechanism; it wrote down a discipline. That works only where the caller both reads the instruction and *can* follow it, and neither holds universally: a caller that dispatches before hitting the DENY never sees it, and **some sessions expose no `run_in_background` parameter on the Agent tool at all** — every dispatch is asynchronous by construction, so "dispatch synchronously" is not an action available to them. Recurrence witnessed 2026-08-10 (addressr `b782a61f`, two full pipeline scores discarded on one commit) and reproduced twice in the 2026-08-20 audit session. **Also do not trust the ticket's stated mechanism**: its title says the hook "does not fire", and the 2026-08-20 evidence does not fit that — two 1-byte files in `.risk-reports/` sit past a guard an empty payload cannot satisfy, and `state-hash` in the risk dir is written by `risk-hash-refresh.sh`, not by the pipeline branch. ## What Will Surprise You

- **A Codex changeset edit can be keyed to the edit payload instead of the normalized changeset body.** P426's unchanged summary passed both external-communications reviewers, but replacing only `patch` with `minor` stayed denied even after body, patch-command, and replacement-line reviews. The governed recovery was a reducing pipeline assessment followed by `npx changeset add`, then removal of the redundant generated patch changeset. Keep the final tree to one authoritative changeset and re-score the live result. <!-- signal-score: 2 | last-classified: 2026-08-31 | first-written: 2026-08-31 -->

- **On Codex, a matching reviewer key is not enough unless the compatibility hook sees the required dispatch shape.** Start the reviewer prompt with `SURFACE: git-commit-message`, wrap the byte-identical message in `<draft>...</draft>`, wait for PASS, then close the completed reviewer once before retrying the commit. A free-form review can return the same `EXTERNAL_COMMS_RISK_KEY` and still leave the gate unmarked; the P512 story commit reproduced that deny-before-correct-dispatch sequence. <!-- signal-score: 1 | last-classified: 2026-08-30 | first-written: 2026-08-30 -->
