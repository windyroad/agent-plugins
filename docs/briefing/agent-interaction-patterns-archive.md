## What Will Surprise You (archived)

- **Write tool fails with "File has not been read yet" after `git mv`.** Renaming a file mid-session invalidates Read-tracking on the new path. `Read` the renamed file before `Write`/`Edit`. (Archived 2026-05-31 — settled discipline.)

- **User-frustration signal: "why are you asking me and not just doing it?"** When a consent gate or "proceed vs discard?" decision is obvious from direction-pinning, policy (risk within appetite), or homogeneous context, ACT first and report — do not defer. Memory: `feedback_act_on_obvious_decisions.md`. (Observed on the install-updates ADR-030 consent gate when the answer was obviously "all 6 siblings.") (Archived 2026-05-31 — codified in CLAUDE.md "act on obvious / AskUserQuestion for ambiguous / NEVER prose-ask" mandate + hook-enforced via `packages/itil/hooks/lib/detectors.sh`.)

- **When the user has a simple persistence-of-knowledge model in mind, the agent's first instinct may build an over-elaborate framing.** On P167 / RISK-POLICY.md the user's `docs/risks/` model was single-universe ("catalog of per-action risks consumed by per-action assessments — same appetite uniformly"); the agent first built a per-action-vs-lifetime aggregation distinction needing two correction rounds, and the misreading propagated into the architect review and ticket framing. **Propose the SIMPLEST persistence-of-knowledge framing first** ("X is the persistent record consumed by Y") and ask whether they want elaboration before building scope-distinction frameworks. A gate's PASS verdict only proves the elaboration is internally consistent, not that it matches the user's intent. (verifying P167; archived 2026-05-31 — instance has settled; pattern is general but the specific P167 trigger no longer recurs.)

- **`git mv` + `Edit` + `git add` requires re-stage after the Edit.** `git mv A B` stages the rename; if you then Edit B and `git add <other-files>` before the final commit, only the rename is captured — the Edit to B stays unstaged and lands in the NEXT commit. Must `git add B` after editing. **Enforced by `packages/itil/hooks/p057-staging-trap-detect.sh` (PreToolUse:Bash on `git commit`)**: denies the commit when a staged rename's new path also appears as a working-tree modification, surfacing the `git add <new>` recovery inline. (closed P057; verifying P125)
- **Validate the problem-ticket framing before asking solution-detail design questions.** When a ticket describes a specific solution, the user may have a different shape in mind; the first `AskUserQuestion` should confirm the framing, not dive into details. (Observed twice on P014 — Other-responses kept recovering from framing misses, collapsing scope and eliminating an ADR.) **If a ticket has already been bounced by a framing miss once, open the next AskUserQuestion with a framing check** ("Is this ticket shape still right — pattern, skill, agent, background subagent, or something else?") before detail questions.
- **Problem-ticket Fix Strategy can describe infrastructure that does not exist.** Ticket authors (often run-retro's Step 2b at session-end) describe what they assume exists rather than what the SKILL.md actually contains; the assumption survives ticket creation, WSJF rating, and AFK selection unchallenged. **Always have the architect verify the ticket's premise about existing infrastructure before drafting the fix** — cost of the check is one architect delegation; cost of skipping it is a wasted iteration shipping the wrong shape. Sibling of the framing-validation rule (user-framing vs architect-premise validation). (closed P121)

- **Decision-confirmation prompts must lead with the substance, not the meta (P302).** When presenting a recorded decision for the user to confirm — `/wr-architect:review-decisions`, `/wr-jtbd:confirm-jobs-and-personas`, and structurally the `/wr-architect:create-adr` Step 5 confirm — open the `AskUserQuestion` `question` field with the one-line Decision Outcome / job statement / persona definition (*what is being decided / asserted*). Sibling-ADR relationships, "separate ADR vs amend" recording-shape, supersession lineage, persona-cluster context: trailing clause or omit. Burying the substance behind meta drove two clarifying re-asks in one session on 2026-05-25 (ADR-045 surfaced as "a sibling ADR codifying five patterns; ADR-038 governs UserPromptSubmit…" → *"if this decision defers to a sibling decision, what does this decision decide??"*; ADR-020 surfaced as "a separate ADR citing ADR-014 + ADR-018 as lineage, keeping single-purpose ADRs" → *"A decision to create a new decision??? What isn't this just the new decision?"*). Both resolved immediately on re-presentation leading with the Decision Outcome. ## Rotated 2026-07-03 (Tier-3 budget)

- **A multi-question `AskUserQuestion` call can return answers for FEWER than all questions** — observed twice in one session (a 4-question batch returned 3 answers each time; the 4th question's answer was silently absent from the response). The dropped question is not flagged as unanswered — it simply doesn't appear in the returned answers map. When you batch N questions, check the returned answers against the questions you asked and **re-ask any that didn't come back** (a single follow-up `AskUserQuestion` with just the missing one). This is a Claude Code harness behaviour, not a windyroad-plugin defect — no plugin-side fix; the discipline is "verify answer-count == question-count, re-ask the gap." (2026-05-26; ADR-018 dropped from one batch, ADR-043 from another.)

- **On a genuine design fork, lead with your reasoning + a recommended option — don't open with a bare "how do you want to proceed?".** 2026-05-26 RFC pivot: the open form drew *"I want your opinion — what do you think?"*. Present the trade-off + a recommendation (architect-first for architecture forks), THEN `AskUserQuestion` to ratify. Distinct from the act-on-obvious rule above: that's for policy/direction-obvious calls (just act); this is for multi-path forks where the user wants your judgment surfaced first (the ratify ask still fires, just after your recommendation).

## Rotated 2026-08-21 (Tier-3 split-by-date from agent-interaction-patterns.md — pre-marker cohort, oldest half)

- **An AFK orchestrator's "sibling / rollup-children" list is a heuristic, not a verified class membership — re-test each named ticket against the actual class definition before rolling up.** The work-problems orchestrator frequently hands a meta-ticket the *current open-ticket set* as candidate children (tickets co-captured in the same recent AFK sessions), not tickets that actually share the class. Worked example (P375 self-firing-cadence meta, 2026-06-28): the orchestrator named 8 siblings (P370/P371/P376/P379/P381/P386/P391/P392); applying the rot-test (deferral reachable from a self-firing trigger?) showed only **P379** was a genuine class member — the other 7 were ordinary defects (gate-branch bug, scanner parity gap, test flake, awk portability, etc.). The authoritative cluster was the one already written in the ticket's own `## Related`. Trust the ticket's curated Related list over the orchestrator's prompt list; verify each candidate, don't rubber-stamp. (2026-06-28, P375.)
- **After `git mv`, the Edit tool requires a fresh Read at the NEW path** — the harness's file-read state does not follow renames; an Edit against the renamed file fails with "File has not been read yet" even when the content was read at the old path moments earlier. Plan ticket-transition flows as: seed-Edit (old path) → `git mv` → Read (new path, a few lines suffice) → Status/Fix-Released Edits → single `git add`. Composes with the P057 staging-trap discipline — same flow, adjacent gotcha. (2026-06-11, P211 K→V transition.)
- **Substance-confirm `AskUserQuestion` requires prose briefing + option-shaped + no-IDs-as-explainers + informed-without-external-lookup (P339 / P340).** Surfaced 2026-05-31 by ADR-078 commit `5196e3d`: a bundled Step 5 "review pass" `AskUserQuestion` ("does the problem statement + Decision Outcome (Option X) capture the situation? — yes/no/edits/different-option") landed `human-oversight: confirmed` on substance the user never explicitly ratified. The user had confirmed only draft quality; Option X was substantially different from the option the user actually wanted (Option 9). User correction: *"I never approved the scripted extraction. You are supposed to run decisions by me"* + *"How did that ADR skip ratification?"*. Five load-bearing requirements when surfacing substance for confirmation: (1) briefing in main-turn PROSE before the question fires (long question text is unreadable on mobile / accessibility tooling / notification surfaces; long prose + short question IS readable across the device matrix); (2) `AskUserQuestion` is option-shaped not yes/no (each considered option a selectable entry; user picks positively); (3) no IDs as explainers (the user does not have `ADR-NNN` / `P-NNN` / `JTBD-NNN` / `RFC-NNN` lookups on all devices — every option's substance self-contained in prose + label); (4) user can make an informed decision without external document lookup (briefing + question + options is self-contained); (5) substance-only at this fire (draft-quality, problem-statement-OK, consulted/informed belong to a SEPARATE later fire). Born-confirmed marker writes ONLY when the substance-confirm answer matches the draft on disk; mismatch triggers re-draft + re-fire (NOT a soft warn-and-proceed). Codified in `/wr-architect:create-adr` SKILL.md Step 5 (split into 5a substance-confirm + 5b draft-quality), ADR-064 § Decision Outcome amendment 2026-05-31, ADR-066 § Decision Outcome item 5 amendment 2026-05-31. Bats coverage at `packages/architect/skills/create-adr/test/create-adr-substance-confirm-pattern.bats`. ADR-074-class — substance pinned before any dependent work (the marker write) lands.
