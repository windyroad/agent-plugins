## The lazy count is a real regression and both calls share one cause

This is the first non-zero lazy count in the trail. Both lazy calls have the same shape, and it
is not the usual one. The usual lazy ask is the agent knowing the framework resolves something
and asking anyway. **Here the agent did not know, because it never opened the artefact** — it
inherited a claim (a queue entry; a detector's output) and built a question on top of it.

So the fix is not "ask less". Asking was reasonable given what the agent believed. The fix is the
read that would have made both asks unnecessary, which is the class now recorded as P434's third
scope extension. Counting them as lazy is the honest classification even though the proximate
error was upstream of the ask.

Both were also costly beyond the friction: call 1 asked the maintainer to re-ratify something they
had ratified three weeks earlier, and call 2 put a question whose framing the maintainer had to
correct ("What are you talking about say they become unfixable?").
