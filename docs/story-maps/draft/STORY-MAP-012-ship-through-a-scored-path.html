What this map traces to

Persona: developer — the person doing the work, with tech-lead secondary for the incident path. Constraint that binds this map: repo shape varies, so anything naming a specific command must discover it rather than assume it.

Jobs mapped: JTBD-002 (ship with confidence) is the spine — its outcome that governance cannot be bypassed is what activity C exists to make true. JTBD-005 (assess on demand) is activity B. JTBD-201 (restore service fast) is the incident bypass in activity E. JTBD-001 (enforce governance without slowing down) and JTBD-003 (compose only the guardrails I need) constrain the whole map — JTBD-003 is why the R1 fix is obligatory rather than nice to have.

Problems this closes: P435 — the gate is hardcoded to this repo's shape, so it over-fires in projects without the pipeline it assumes (the R1 band). P208 — CI status was not checked before scoring, now shipped in the Live band.

Decisions the journey rests on: The push and release gates, the drift-revalidated bypass markers, and the CI precondition. Note that none of this is recorded as a control in docs/risks/ — the funnel exists only as a property of the dispatch order and one deny branch, which is how it was nearly read as a workflow convention rather than a safety control.

Open questions: Whether the concerns on this map and on STORY-MAP-013 ship as one plugin or two is undecided as of 2026-08-05. Both involve blocks, so 'one blocks, the other reports' is not the dividing line. The push to a pipeline-owned branch in activity C has a genuine claim on both maps and is recorded here rather than resolved.
